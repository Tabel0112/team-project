This is reviewable setup material. The application does not execute migrations. Live Supabase integration is unverified until these steps are completed in a configured project.

1. Create/choose a Supabase project with the Data API enabled. Automatic table exposure may stay disabled: the script explicitly grants access. In Auth, enable email/password and decide whether email confirmation is required. Keep confirmation enabled for a normal project.
2. Review `uc5_setup.sql` against the project schema, then apply it once in SQL Editor as the project owner. It creates fresh `public.uc5_study_sets`, `public.uc5_flashcards`, `public.uc5_save_receipts`, and the two `uc5_*` RPC functions. Existing objects with those names cause the transaction to fail; do not drop existing tables to force installation. It does not alter unrelated tables.
3. Set `SUPABASE_URL` and the public publishable/legacy anon key using the placeholders in the main README. Keep `.env` ignored. Do not use a database password, secret key, or service-role key in the desktop client.
4. Start `app.Main`, sign up if necessary, confirm the email, and log in. Signup is not performed automatically by tests or startup.
5. Create a local set, add cards or generate from notes, and click Save. Close and restart, log in, open the set, and verify its name, card text, UUIDs, and order. New local sets/cards should not appear in the database until Save.
6. Disconnect networking before Save: the UI must retain the draft and allow retry. Test a response-loss retry in a controlled test environment and verify one set/card per stable ID. Receipts persist operation payloads so retried requests return the original revision rather than reapply changes.
7. In a disposable test project, use two real authenticated users to verify A cannot list, load, insert into, update, or delete B's sets, cards, or receipts, including card IDs submitted to the Save RPC. Verify anonymous access and anonymous RPC invocation are denied. Use user JWTs, not a privileged SQL Editor session, for these checks.
8. Open the same saved set in two app sessions: save from the first, then save from the second. The second should receive a revision conflict with its draft preserved. Automatic conflict merging is not implemented; preserve/reconcile the draft before explicitly discarding it and reloading.

`uc5_save_set` is a security-invoker function: the caller's user JWT, table grants, and RLS apply. Set ownership is derived from `auth.uid()`, never a client-provided owner. Card policies look through the owning set. Upserts cannot move an existing card into another set. An advisory transaction lock serializes first saves and retries for a set; the revision check rejects stale commits. Set metadata, card deltas, deletes, and the receipt share a single database transaction. The load RPC reads metadata and all cards in one SQL statement, avoiding split reads and API row-limit truncation.

Inherited/default PUBLIC, anonymous, and authenticated table grants are reset explicitly. Authenticated users receive select/insert/update/delete on sets/cards and select/insert on receipts, restricted to their own rows by RLS. Clients that bypass these RPCs can modify their own rows directly; revision conflict detection assumes application writes use the Save RPC. No global/public demo policy or service-role access is used. Receipts retain a historical copy of submitted text to support ambiguous retries; no retention/deletion job is configured. Do not remove receipts while clients may retry pending operations.
